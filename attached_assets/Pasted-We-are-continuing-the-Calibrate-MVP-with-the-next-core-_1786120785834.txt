--------------------------------------------------
PRIMARY GOAL
--------------------------------------------------

Complete the next part of the real Calibrate experiment loop:

Study Session
↓
Session Complete
↓
“How’d it go?”
↓
Post-session feedback
↓
Context about WHY the result happened
↓
Persist feedback
↓
Insights can later interpret the result correctly

The student should not simply finish a quiz and immediately see an analytics dashboard.

Calibrate needs a small amount of context about the session first.

--------------------------------------------------
1. PRODUCT PRINCIPLE
--------------------------------------------------

A low score does NOT automatically mean:

“The study technique failed.”

Possible causes include:

- the technique did not work well
- the generated questions were poor
- the material was especially difficult
- the student was distracted / low energy
- other session conditions

The post-session flow should capture this context before Insights interprets the session.

Do NOT automatically change the recommended technique based on one session.

--------------------------------------------------
2. INSPECT EXISTING ARCHITECTURE FIRST
--------------------------------------------------

Before changing code, inspect:

- current session completion state
- /api/sessions
- /api/outcomes
- outcome/session database schema
- existing feedback APIs/routes if any
- current Insights page/data loading
- any existing post-session Figma-inspired UI
- current seeded/demo outcome data

Reuse existing architecture.

Do NOT create a parallel analytics or feedback system if one already exists.

--------------------------------------------------
3. SESSION COMPLETION HANDOFF
--------------------------------------------------

After a REAL Study Session successfully persists its session/outcome:

the primary next action should be:

“Continue”

and should enter the post-session feedback flow.

Do not immediately route the student to Dashboard or Insights.

The intended path is:

Study Session
→ Session complete
→ Post-session feedback

Preserve the completion summary already implemented.

--------------------------------------------------
4. POST-SESSION SCREEN 1
--------------------------------------------------

Create/refine the first post-session feedback screen using the Calibrate Figma direction.

Heading:

“How’d it go?”

Provide a simple overall experience choice:

Rough
Good

Use large selectable cards/buttons.

Also capture a lightweight session-state measure.

Use the existing Figma concept:

“Anxiety while studying”

Calm ←────────→ Wired

If the current product direction uses focus/energy instead and that fits the existing data architecture better, use the existing terminology rather than inventing a new psychological metric.

Keep this interaction lightweight.

Do NOT turn it into a long survey.

--------------------------------------------------
5. RESULT CONTEXT / SCORE DIP
--------------------------------------------------

If the student:

- marks the session as Rough
OR
- has a meaningfully poor recorded performance based on existing outcome data

show the next contextual question:

“Score dipped today — what happened?”

Supporting text:

“Select all that apply”

Options:

- Technique wasn’t right
- Questions weren’t right
- Material was hard
- Distracted / low energy

Use the existing Figma/product wording where practical.

Allow multiple selections.

Do not force the student to choose an explanation if they genuinely do not know.

If useful, include:

“Not sure”

as a secondary option.

--------------------------------------------------
6. GOOD SESSION PATH
--------------------------------------------------

If the student reports the session went well:

do not force them through the negative-cause screen.

Allow them to submit the shorter feedback path.

Conceptually:

Good
→ session-state slider
→ Submit

Keep the workflow fast.

--------------------------------------------------
7. QUESTIONS WEREN’T RIGHT
--------------------------------------------------

This option is especially important because Calibrate uses AI-generated questions.

If the student selects:

“Questions weren’t right”

record that fact separately from:

“Technique wasn’t right”

Do NOT interpret bad-question feedback as evidence that the study technique failed.

Where practical, later Insights should be able to identify sessions whose results may have been confounded by question quality.

Do NOT automatically delete or reject questions during this feedback step.

A later UI may link the student back to Question Bank for review.

--------------------------------------------------
8. FEEDBACK DATA MODEL
--------------------------------------------------

Inspect the current outcomes/feedback schema.

Persist the smallest useful structured feedback representation.

We need to preserve enough information to know:

- which completed session this feedback belongs to
- overall session feeling (Rough / Good)
- session-state slider value
- selected reason(s), if any
- timestamp if existing architecture supports it

Prefer existing tables/fields.

If a small schema addition is genuinely required:

explain exactly what is missing and make the smallest safe migration.

Do not redesign unrelated schemas.

--------------------------------------------------
9. STRUCTURED REASON VALUES
--------------------------------------------------

Store machine-readable values rather than only display strings.

Conceptually:

technique_wrong
questions_wrong
material_hard
distracted_low_energy
not_sure

Use naming conventions consistent with the existing project.

UI should show student-friendly labels.

--------------------------------------------------
10. SESSION OWNERSHIP
--------------------------------------------------

Feedback submission must verify:

- the completed session belongs to the current user
- the user cannot submit feedback for another user’s session

Do not trust a sessionId from the browser without server-side ownership validation.

--------------------------------------------------
11. PARTIAL-SAVE SAFETY
--------------------------------------------------

Address the remaining suggested safety issue as part of this milestone:

A completed session must not become silently inconsistent if:

- the session record saves
- but its outcome or feedback write fails

Use the existing completionKey/idempotency architecture.

Do NOT create duplicate completed sessions when retrying.

Preferred behavior:

If the Study Session result is already safely persisted but feedback fails:

- preserve the completed session
- show a recoverable feedback error
- allow feedback submission to retry
- do not create a second session

If outcome persistence itself fails:

- do not pretend the session was fully saved
- provide a clear retry/recovery path
- reuse the same completion identity where applicable

Add tests for this behavior.

--------------------------------------------------
12. SUBMISSION
--------------------------------------------------

Primary CTA:

“Submit”

or:

“Save feedback”

After a successful feedback save:

route toward the next appropriate experience.

For this milestone, prefer:

→ Insights

because the next step in the Calibrate loop is understanding the accumulated evidence.

Do NOT rebuild Insights fully in this task.

A minimal route handoff is sufficient.

--------------------------------------------------
