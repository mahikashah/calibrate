We are beginning the end-to-end Calibrate ML integration milestone.

IMPORTANT CONTEXT

Before making changes, read:

- replit.md
- docs/CALIBRATE_MASTER_CONTEXT.md
- docs/ML_INTEGRATION_CONTRACT.md
- ml-service/README.md

The isolated FastAPI ML service is already implemented and tested.

It currently provides:

GET /health

POST /parse-pdf

POST /generate-questions

The FastAPI service currently runs locally in this Replit project with:

PYTHONPATH=ml-service python -m uvicorn app.main:app --host 0.0.0.0 --port 8000

The existing Next.js app remains on port 5000.

The ML service wraps Shreya's Python pipeline using:

- pdfplumber
- Hugging Face Inference Router
- Qwen/Qwen2.5-7B-Instruct
- structured question output

This milestone should CONNECT the existing Calibrate application to that FastAPI service.

--------------------------------------------------
PRIMARY GOAL
--------------------------------------------------

Create the first real end-to-end Calibrate generation flow:

Subject
→ Add Material
→ PDF or Paste Notes
→ Next.js server
→ FastAPI
→ Shreya's generation pipeline
→ structured questions
→ Calibrate database
→ Question Bank

The browser must NOT communicate directly with Hugging Face.

The browser should also NOT communicate directly with FastAPI.

The request path must remain:

Browser
→ Next.js
→ FastAPI
→ Hugging Face

--------------------------------------------------
1. ENVIRONMENT VARIABLES
--------------------------------------------------

Use:

ML_SERVICE_URL

to locate FastAPI.

For current Replit development this may be:

http://127.0.0.1:8000

Use:

ML_SERVICE_API_KEY

for the server-to-server authentication header expected by FastAPI.

Do NOT hardcode either value.

Do NOT expose ML_SERVICE_API_KEY in browser/client-side JavaScript.

HF_TOKEN belongs only to the Python ML service.

The Next.js application should never need HF_TOKEN.

- material ownership validation

3. PRESERVE OWNERSHIP VALIDATION
--------------------------------------------------

The existing Next.js application remains responsible for:

Never trust browser-supplied ownership identifiers blindly.

Preserve the existing 404/validation behavior already established by the application where practical.

--------------------------------------------------

POST /generate-questions

Preserve a mock provider/test path if the existing automated test architecture relies on it.

--------------------------------------------------
6. GENERATION REQUEST
--------------------------------------------------

FastAPI expects:

{
  "subject": "Neuroscience",
  "text": "...",
  "requested_count": 6
}

Construct this request server-side.

The subject name should come from the verified database subject.

The text should come from the verified material or approved incoming material workflow.

Do NOT send FastAPI:

- userId
- subjectId
- materialId
- sessionId

unless there is an actual ML requirement.

Those remain Next.js application concerns.

--------------------------------------------------
7. FASTAPI AUTH HEADER
--------------------------------------------------

If ML_SERVICE_API_KEY is configured, send:

X-ML-Service-Key: <ML_SERVICE_API_KEY>

from the Next.js server.

Never send this header from browser code.

--------------------------------------------------
8. HANDLE FASTAPI RESPONSE
--------------------------------------------------

FastAPI returns:

{
  "questions": [
    {
      "type": "active_recall",
      "question": "...",
      "answer": "...",
      "answer_choices": [],
      "source_excerpt": "..."
    }
  ]
}

Supported types:

active_recall
mcq
feynman
fill_in_blank

Validate this response again on the Next.js side before database persistence.

Do not blindly trust even the internal ML service.

Use Zod or the project's existing validation approach.

--------------------------------------------------
9. INSPECT DATABASE QUESTION SCHEMA
--------------------------------------------------

We need to preserve:

- type
- question
- answer
- answer choices
- source excerpt/supporting context
- subject relationship
- material relationship

Also inspect whether an approval/review status already exists.

IMPORTANT:

Do not silently drop answer, answer_choices, or source_excerpt merely because the old schema did not support them.

If the existing schema already has appropriate equivalent fields:

reuse them.

If fields are genuinely missing:

make the SMALLEST necessary schema change to persist the real structured question format.

Before making a schema change, clearly identify:

- what is missing
- why persistence requires it
- the minimal migration needed

Do not redesign unrelated tables.

15. PDF ERRORS
--------------------------------------------------

Translate structured FastAPI errors into useful student-facing responses.

Examples:

UNSUPPORTED_PDF

Student-facing meaning:

“This PDF appears to be scanned. Try a text-based PDF or paste your notes instead.”

NOTES_TOO_LONG

Student-facing meaning:

“This material is too long. Try one lecture, chapter, or study section at a time.”

MODEL_TIMEOUT

Student-facing meaning:

“Question generation took too long. Please try again.”

INVALID_MODEL_RESPONSE

Student-facing meaning:

“We couldn't generate valid questions from this material. Please try again.”
