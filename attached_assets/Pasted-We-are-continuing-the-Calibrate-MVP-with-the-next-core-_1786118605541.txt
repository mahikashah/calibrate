--------------------------------------------------
PRIMARY GOAL
--------------------------------------------------

Turn the existing Study Session into the real next step after Question Bank review.

The intended flow should become:

Approved Questions
→ Start Study Session
→ Work through approved questions
→ Reveal/check answers
→ Record results
→ Complete session
→ NEXT milestone: Post-session Feedback

This milestone should make Study Session FUNCTIONAL with the real structured question data.

Do NOT redesign Insights or Dashboard yet.

--------------------------------------------------
1. INSPECT EXISTING STUDY ARCHITECTURE FIRST
--------------------------------------------------

Before changing code, inspect:

- src/app/study/page.tsx
- existing Study Session components
- /api/sessions
- /api/outcomes
- current session/database schema
- current Study Session seeded/demo behavior
- current technique-selection logic
- current recommendation/suggested-technique behavior
- existing timer/session-duration behavior
- current Figma-inspired study screens

Reuse the existing architecture wherever possible.

Do NOT create a parallel Study Session system.

--------------------------------------------------
2. REAL VS DEMO SESSION RULE
--------------------------------------------------

Preserve presentation-friendly seeded/demo Study Session content.

However:

When a student enters Study Session from Question Bank with a real:

subjectId
and/or
materialId

the session must use ONLY approved questions belonging to that verified context.

Do NOT silently mix seeded demo questions into a real subject/material session.

If no approved questions exist for that real context:

show:

“No approved questions are ready for this session.”

and provide:

“Back to Question Bank”

Do NOT substitute demo questions automatically.

Existing seeded/demo sessions may remain accessible separately for presentation purposes.

--------------------------------------------------
3. QUESTION BANK HANDOFF
--------------------------------------------------

The existing Question Bank:

“Start study session”

action should carry the selected context into Study Session.

Prefer query/context such as:

/study?subjectId=...&materialId=...

or the smallest route structure consistent with the current implementation.

On Study Session load:

- verify the subject belongs to the current user
- verify material context if supplied
- fetch ONLY approved questions
- preserve ownership/data isolation

Do not trust browser IDs blindly.

--------------------------------------------------
4. STUDY SESSION START SCREEN
--------------------------------------------------

Refine the Study Session entry state so the student clearly sees:

STUDY SESSION

Subject:
[Selected Subject]

Material:
[Selected Material] if applicable

Suggested technique:
[Existing Calibrate recommendation]

Approved questions available:
[#]

Then show the existing technique choices.

Preserve the current technique system rather than inventing a new recommendation algorithm.

Possible existing techniques may include:

- Active Recall
- Spaced Repetition
- Feynman / Self-Explanation
- Practice Questions
- Re-reading control

The recommendation should remain transparent.

Do NOT let an LLM choose the technique.

--------------------------------------------------
5. TECHNIQUE VS QUESTION TYPE
--------------------------------------------------

Keep these concepts separate:

STUDY TECHNIQUE
= the experiment the student is testing

QUESTION TYPE
= how an individual generated question is rendered

Do not assume they are identical.

For this MVP:

- preserve the selected technique as session metadata
- render each approved question according to its structured question type

Question types currently supported:

active_recall
mcq
feynman
fill_in_blank

Do not invent new ML question types.

--------------------------------------------------
6. SESSION PROGRESS
--------------------------------------------------

When the student starts:

show one question at a time.

Display clear progress such as:

Question 1 of 6

Use a subtle progress indicator.

Also preserve/use the existing session timer if one exists.

The experience should feel focused and distraction-free.

--------------------------------------------------
7. ACTIVE RECALL RENDERING
--------------------------------------------------

For:

type = active_recall

Show:

- “Active Recall”
- question/prompt
- text answer field
- timer/progress
- Submit and reveal

After submission:

show:

“Your answer”

and:

“Suggested answer”

Do NOT use another LLM call to judge free-response answers in this milestone.

Instead provide a simple self-assessment:

“Got it”
“Missed it”

or similarly clear wording.

Record that result using the existing outcome/session architecture where possible.

--------------------------------------------------
8. MULTIPLE CHOICE RENDERING
--------------------------------------------------

For:

type = mcq

Show:

- Multiple Choice
- question
- four answer choices
- one selectable choice
- Submit

After submit:

compare the selected answer against the stored correct answer.

Show clearly:

Correct

or:

Not quite

If incorrect:

show the correct answer.

Do not reveal the correct answer before submission.

Record the result automatically.

--------------------------------------------------
9. FILL IN THE BLANK RENDERING
--------------------------------------------------

For:

type = fill_in_blank

Show:

- Fill in the Blank
- question
- short answer input
- Submit and reveal

For MVP grading:

normalize simple differences such as:

- leading/trailing whitespace
- capitalization

Do NOT build complicated semantic grading.

After submission:

show the expected answer.

If exact/simple normalized comparison is unreliable for a given answer:

allow the same self-assessment approach used by Active Recall.

Do not call an LLM judge.

--------------------------------------------------
10. FEYNMAN RENDERING
--------------------------------------------------

For:

type = feynman

Use the Figma/product direction.

Show:

“Feynman / Self-Explanation”

Question/prompt

Large textarea:

“Explain it in your own words…”

After submit/reveal:

show:

- student explanation
- suggested/reference answer
- supporting notes where useful

Then ask for simple self-assessment such as:

“Good”
“Needs work”

Do NOT use an LLM judge in the live session.

--------------------------------------------------
11. SUPPORTING SOURCE
--------------------------------------------------

Preserve sourceExcerpt/supporting notes.

During Study Session:

do NOT show sourceExcerpt before the student attempts the question.

After reveal:

allow an optional:

“View supporting notes”

section.

This helps students understand where the answer came from without giving away the answer beforehand.

--------------------------------------------------
12. QUESTION ORDER
--------------------------------------------------

For the MVP:

use the approved questions belonging to the selected subject/material.

Do not include:

generated
edited
rejected

questions.

A reasonable stable order is acceptable.

If the existing application already randomizes or orders questions deliberately, preserve that behavior.

Do not add complicated adaptive sequencing yet.

--------------------------------------------------
13. RE-READING CONTROL
--------------------------------------------------

If the existing Study Session supports:

Re-reading (control)

preserve it.

Re-reading is different from generated-question practice.

For a re-reading session:

- show the selected material text
- preserve timer behavior
- allow “Done reading”
- record the session technique as the re-reading/control condition

Do not force Question Bank questions into the re-reading screen.

If the selected material text is not available:

show a clear message rather than fake content.

--------------------------------------------------
14. SPACED REPETITION
--------------------------------------------------

Do NOT build a full scheduling engine in this milestone.

If the existing app already has spaced-repetition behavior:

preserve it.

Otherwise:

- record the selected technique as spaced repetition
- use the approved questions in the normal recall/reveal session flow
- document that future scheduling/cadence is a later refinement

Do not overbuild SM-2 or another scheduling algorithm right now.

--------------------------------------------------
15. PRACTICE QUESTIONS TECHNIQUE
--------------------------------------------------

If the student selects:

Practice Questions

use the approved question set normally.

MCQ and Fill in the Blank should use automatic/simple grading where possible.

Active Recall/Feynman responses may use self-assessment.

--------------------------------------------------
16. SESSION CREATION
--------------------------------------------------

Use the existing /api/sessions architecture.

When a real study session starts:

create/use the existing session record with the appropriate existing fields.

Preserve:

- current user
- subject
- selected technique
- start/session timing
- existing session model

Do NOT create a second session table or parallel persistence system.

If materialId is not currently stored on sessions and adding it would require a substantial migration:

do not overbuild it in this task.

Use the existing architecture and report the limitation.

--------------------------------------------------
17. SESSION RESULTS
--------------------------------------------------

As the student works through questions, track enough information to produce:

- total questions attempted
- correct / successful count where applicable
- missed / needs-work count
- elapsed time
- technique used
- subject
- completion state

Reuse:

/api/outcomes

or the existing result/outcome persistence where appropriate.

Do not invent a second analytics system.

--------------------------------------------------
18. SESSION COMPLETION
--------------------------------------------------

After the final question:

show a simple session completion state.

Example:

“Session complete”

Then display:

Questions reviewed:
6

Got it / correct:
4

Needs work:
2

Focused time:
12m

Technique:
Active Recall

Do NOT build the full post-session reflection UI in this task.

Provide a clear CTA:

“Continue”

The next milestone will turn that into the full:

How’d it go?
→ Rough / Good
→ anxiety/focus
→ Why did the score dip?

flow.

If an existing post-session route already exists, preserve/use it.

Otherwise keep the completion handoff minimal and clearly document the next integration point.

--------------------------------------------------
19. DO NOT AUTO-UPDATE THE RECOMMENDATION YET
--------------------------------------------------

Completing one Study Session should record the result.

Do NOT redesign the recommendation engine in this milestone.

Do NOT immediately declare a technique the winner.

The later Insights/recommendation milestone will use multiple real outcomes.

--------------------------------------------------
