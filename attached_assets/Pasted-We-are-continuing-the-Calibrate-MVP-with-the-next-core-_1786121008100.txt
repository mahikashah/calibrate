--------------------------------------------------
1. PRODUCT PRINCIPLE
--------------------------------------------------

A low or difficult session must NOT automatically mean:

“The study technique failed.”

Possible reasons include:

- the study technique was not effective
- the generated questions were poor
- the material was unusually difficult
- the student was distracted or low energy

Calibrate must capture this context separately.

Do NOT immediately change the student’s recommended technique based on one session.

--------------------------------------------------
2. INSPECT EXISTING ARCHITECTURE FIRST
--------------------------------------------------

Before changing code, inspect:

- current Study Session completion state
- /api/sessions
- /api/outcomes
- any existing /api/feedback route
- session/outcome/feedback database schema
- current completion redirect behavior
- current Insights data loading
- any existing feedback UI/components
- existing seeded/demo outcome history
- the Calibrate Figma-inspired post-session screens

Reuse existing architecture.

Do NOT create a parallel feedback or analytics system if one already exists.

--------------------------------------------------
3. STUDY SESSION COMPLETION HANDOFF
--------------------------------------------------

After a REAL Study Session successfully saves its session and outcome:

the primary completion action should become:

“Continue”

and lead into the real post-session feedback experience.

Do NOT send the student directly to:

- Dashboard
- Insights
- Question Bank

The intended sequence is:

Study Session
→ Completion Summary
→ Post-session Feedback

Preserve the existing completion summary.

--------------------------------------------------
4. POST-SESSION ROUTE
--------------------------------------------------

Use the smallest route structure consistent with the existing application.

Prefer something clear such as:

/feedback?sessionId=...

or an existing feedback route if one already exists.

The session identifier may come from the browser, but the server MUST verify ownership before reading or writing feedback.

Do not trust sessionId blindly.

--------------------------------------------------
5. POST-SESSION SCREEN 1
--------------------------------------------------

Build/refine the first feedback screen using the Calibrate Figma direction.

Heading:

“How’d it go?”

Provide two large selectable options:

Rough

Good

These should feel like large Calibrate choice cards rather than generic radio buttons.

Also capture one lightweight state measure.

Use the existing Figma concept:

“Anxiety while studying”

Calm ←────────→ Wired

If the current implementation already has a better-established focus/energy field, preserve the existing terminology rather than creating duplicate concepts.

Keep this fast.

Do NOT turn this into a long questionnaire.

--------------------------------------------------
6. GOOD SESSION PATH
--------------------------------------------------

If the student chooses:

Good

do not force them through negative-cause questions.

Expected flow:

Good
→ state slider
→ Submit

The student should be able to complete this path in a few seconds.

--------------------------------------------------
7. ROUGH / LOW-PERFORMANCE PATH
--------------------------------------------------

If:

- the student selects Rough

OR

- the saved outcome indicates meaningfully poor performance using an existing simple threshold

show a second context screen.

Heading:

“Score dipped today — what happened?”

Supporting text:

“Select all that apply”

Options:

- Technique wasn’t right
- Questions weren’t right
- Material was hard
- Distracted / low energy

Optionally include:

- Not sure

Allow multiple selections.

Do not require the student to invent an explanation.

--------------------------------------------------
8. MACHINE-READABLE REASON VALUES
--------------------------------------------------

Persist structured values rather than only display strings.

Use naming consistent with the existing project.

Conceptually:

technique_wrong
questions_wrong
material_hard
distracted_low_energy
not_sure

The student-facing labels remain natural language.

--------------------------------------------------
9. QUESTIONS WRONG VS TECHNIQUE WRONG
--------------------------------------------------

This distinction is essential.

If:

questions_wrong

is selected:

store it separately from:

technique_wrong

Do NOT interpret question-quality problems as evidence that the study technique itself failed.

This is especially important because Calibrate uses AI-generated practice questions.

Do not automatically delete or reject questions during this feedback flow.

A later experience may link back to Question Bank.

--------------------------------------------------
10. FEEDBACK DATA
--------------------------------------------------

Persist the smallest useful structured feedback representation.

We need to know:

- session
- current user through session ownership
- overall feeling: Rough / Good
- slider/state value
- selected reason values
- timestamp if supported by current architecture

Prefer existing tables/fields.

If the existing schema is insufficient:

identify exactly what is missing.

Make the smallest safe migration required.

Do NOT redesign unrelated session/outcome tables.

--------------------------------------------------
11. OWNERSHIP
--------------------------------------------------

Feedback APIs must verify:

the completed session belongs to the current user.

A user must not:

- read another user’s session feedback
- submit feedback for another user’s session
- overwrite another user’s feedback

Preserve the same ownership principles used throughout Calibrate.

--------------------------------------------------
12. RETRY / PARTIAL-SAVE SAFETY
--------------------------------------------------

Build on the existing retry-safe session completion architecture.

If:

session + outcome already saved successfully

but:

feedback save fails

then:

- preserve the completed session
- do NOT create another session
- show a recoverable feedback error
- allow the student to retry feedback submission

If feedback is submitted twice due to a retry:

do not create duplicate feedback evidence.

Use idempotent/upsert behavior where appropriate.

--------------------------------------------------
13. DO NOT MODIFY SESSION RESULTS
--------------------------------------------------

Post-session feedback provides CONTEXT.

It should not overwrite:

- answer correctness
- question results
- elapsed time
- session technique
- outcome score

Those remain objective session data.

Feedback is a separate layer explaining possible conditions around that result.
