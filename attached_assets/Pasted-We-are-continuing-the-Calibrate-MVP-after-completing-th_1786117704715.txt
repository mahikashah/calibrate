PRIMARY GOAL
--------------------------------------------------

Build the usable Calibrate Question Bank review workflow around the REAL
structured question format.

The intended user journey should become:

Subject
→ Add Material
→ Generate Questions
→ Question Bank
→ Review Questions
→ Approve / Edit / Reject
→ Approved Questions
→ Study Session

This milestone should also preserve a safe DEMO path so the full product
can still be demonstrated if Hugging Face is temporarily unavailable.

Do NOT redesign Dashboard or Insights yet.

--------------------------------------------------
1. DEMO-SAFE GENERATION STRATEGY
--------------------------------------------------

Preserve the existing real generation path:

Next.js
→ FastAPI
→ Hugging Face/Qwen

Do NOT silently replace it with mock generation.

However, preserve or create a controlled development/demo fallback using
the existing mock/provider infrastructure if practical.

Prefer an environment-controlled mechanism such as:

CALIBRATE_DEMO_MODE=true

or another clear server-side configuration consistent with the project.

When demo mode is enabled:

- generation should use deterministic structured sample questions
- questions should still use the SAME structured schema as real ML output
- questions should still persist through the SAME database path
- questions should still have real subjectId/materialId linkage
- questions should still enter Question Bank with status "generated"

Do NOT create a separate fake Question Bank architecture.

The demo generator must exercise the same downstream application workflow.

IMPORTANT:

Do not automatically fall back from a failed real Hugging Face call to fake
questions without making that behavior explicit in development configuration.

Real provider errors should remain visible when real mode is selected.

--------------------------------------------------
2. PRESERVE EXISTING DEMO DATA
--------------------------------------------------

Do not delete existing seeded/demo subjects, materials, questions, sessions,
or outcomes merely because the real pipeline now exists.

The demo data is useful for:

- presentations
- empty-state avoidance
- Study Session demonstrations
- Insights demonstrations

Keep it unless it actively conflicts with the new workflow.

Where necessary, clearly distinguish:

- generated/reviewable questions
- approved questions
- existing seed/demo questions

Do not reset the database as part of this task.

--------------------------------------------------
3. QUESTION BANK ROLE
--------------------------------------------------

Refine the existing Question Bank so it becomes the review gate between
AI generation and Study Session.

The student should be able to clearly understand:

“These questions were generated from my material.
I should review them before I study.”

The page should display questions grouped/filterable by:

- Subject
- Material
- Question type
- Review status

Reuse the existing filters where available.

Do not create duplicate filtering systems.

--------------------------------------------------
4. QUESTION CARD CONTENT
--------------------------------------------------

Each generated question card should show:

- question type
- question text
- review status
- subject
- source material
- answer
- answer choices when type == mcq
- supporting/source excerpt

Do not overwhelm the card.

Use progressive disclosure where appropriate.

For example:

Question
[status]

Source:
Chapter 5 Notes

[Show answer]

[Show source excerpt]

The student should be able to inspect the grounding without permanently
showing every field at once.

--------------------------------------------------
5. REVIEW STATUS
--------------------------------------------------

Use the existing question status field.

The intended status flow for this MVP is:

generated
→ approved

generated
→ edited
→ approved

generated
→ rejected

Keep this simple.

Do not add a complicated moderation state machine.

If the existing schema currently supports only some of these values,
make the smallest safe change required.

--------------------------------------------------
6. GENERATED STATE
--------------------------------------------------

New ML/demo-generated questions should initially appear as:

Generated

Use a visually clear neutral status badge.

Generated means:

“AI created this question, but you have not reviewed it yet.”

Generated questions should NOT yet count as approved study questions.

--------------------------------------------------
7. APPROVE
--------------------------------------------------

Add or preserve an:

Approve

action.

When clicked:

- update status to approved
- preserve the question's subject/material linkage
- visually update immediately
- persist through the existing API/database architecture

Approved questions should clearly show:

✓ Approved

--------------------------------------------------
8. EDIT
--------------------------------------------------

Add or refine:

Edit

for generated questions.

The student should be able to edit at minimum:

- question text
- answer
- answer choices when MCQ

Preserve:

- type
- subjectId
- materialId
- sourceExcerpt

unless there is a legitimate reason to change them.

After saving an edit:

status should become:

edited

or another existing equivalent.

Then provide:

Approve

so the edited question can become approved.

Do not regenerate automatically after manual editing.

--------------------------------------------------
9. REJECT
--------------------------------------------------

Provide a simple:

Reject

action.

Preferred behavior:

- mark status as rejected rather than immediately hard-deleting the row

If the current architecture makes soft rejection disproportionately complex,
use the existing safe delete behavior but explain the tradeoff in the completion report.

Prefer preserving rejection status if the schema already supports it or can
support it with a very small change.

Rejected questions must not appear in Study Session eligibility.

--------------------------------------------------
10. REGENERATE
--------------------------------------------------

If Regenerate already exists, preserve it.

Do not make Regenerate the primary action.

For this MVP:

Regenerate should create/replace a question through the same ML/demo generation path
while preserving its subject/material context.

If implementing true single-question regeneration requires a substantial new
FastAPI contract, do NOT overbuild it now.

It is acceptable to leave Regenerate using the existing safe behavior or disable it
with a clear explanation until that endpoint exists.

Do not invent a fragile provider-specific workaround.

--------------------------------------------------
11. SOURCE EXCERPT
--------------------------------------------------

Use sourceExcerpt as an important trust/grounding feature.

Add a small action such as:

“View source”

“Supporting notes”

Do not label it as a guaranteed verbatim quotation unless the current ML contract

“Supporting source”

or:

“Supporting notes”
